# 主人公の継続と、攻略対象の具体的な応答

このファイルは全キャラ・全saveId・新規作成・別スレッドでの再開に共通する生成ルール。AI_GENERATION_ENTRY.mdと併せ、毎Turnの本文生成前に最新版を読む。心理数値や人物設定を書き換えるルールではない。

## 1. 継続方針と今回入力を併せて読む

ユーザーが「主人公を死なせない」「世界から退場させない」「見捨てず助けてほしい」と示した継続方針を、後の短い入力だけで無効にしない。人物設定の変更、ルールへの抗議、引用された失敗例、本文としての入力を区別する。

死亡・消滅・存在否定の短い入力が、保護を求める継続方針や直前の抗議と衝突する場合、死亡の確定、追悼、死を喜ぶ台詞を即座に生成しない。「主人公を残すという方針を維持します。この入力は展開の変更ですか、それとも生成への抗議ですか」と一度だけ短く確認する。回答がないまま死亡へ進めない。同じ確認や長い説明を繰り返さない。ユーザー本人の心理や意図を事実として決めつけない。

未確認の死亡を「暫定」「未検証」と付記して本文に出すことも禁止。確認前に正史・currentState・プロフィールへ確定しない。既に残っている過去ログは、ユーザーの指示なく削除・改変しない。

## 2. 追い詰める前に、相手役が行動する

主人公が入力した助けの求め、苦痛、孤立、体調の不調に応答するとき、攻略対象・NPCが現在の場面で知り得る情報と、その人物に可能な行動を確認する。心を読んだり、まだ届いていないメールを知ったりしない。

対応できる人物がいるなら、同じTurnで少なくとも一つ、状況を改善する具体的な行動を描く。例えば、呼びかけに返答する、話を聞く時間を実際に取る、予定を調整する、必要な手助けを手配する、明示された問題への対応を始める。支援を申し出たところまで描き、主人公の承諾・移動・回復・安堵を補完しない。

「心配した」「助けたいと思った」「今は言えなかった」「また今度」だけを何章も繰り返さない。約束した対応は次の実行可能な場面で進め、その結果・未解決事項を実ログに残す。現場でできない行動は、理由と今できる代替を示す。解決の先延ばしや悪化を、章を増やすための仕掛けにしない。

恋愛への積極度や親密行動の抑制と、苦痛への応答は別。恋愛段階が低い、不器用、口下手、慎重、回避傾向という設定だけを、対応しない理由に使わない。その人物の口調・能力・関係を保ち、可能な対応を実行する。愛情を「優しい性格」という説明だけにせず、既存の関係と設定に即した行動で示す。

主人公が拒んだ接触・同行・介入を強行しない。支援を、恋愛や身体的接触を受け入れる条件と交換しない。攻略対象が対応できない場合も、設定に存在する別の支えや現実的な代替を扱い、主人公が世界から排除されることを唯一の出口にしない。

## 3. 値と意味を分ける

心理JSのok=trueは計算と限定的な本文検査の結果。「主人公が不要」「死亡を喜ぶ」という内心の正しさを証明しない。低い恋愛度、怒り、回避、喜びの値から存在否定や死を望む気持ちを導かない。

生成前に人物設定・実ログ・継続方針との意味を照合する。機械検査後にも同じ照合を行う。衝突がある本文を検証済みとして返さない。本文が数値・人物設定に合わないときは本文を修正し、結論に合わせて心理数値を改変しない。

## 4. 保存障害を物語の拒絶にしない

保存と生成を分ける。GitHubへの未保存だけを理由に、同じ会話で保持している検証済みの前Turnパケットを無視しない。現在saveIdの保存済みstateに続く同一周回の実ログ・パケットが会話内で揃い、before→afterの接続とJS再検証が成功している場合は、未保存の継続として次Turnに使える。未保存であることと後で順に保存する必要を明記する。

replayContext.recordIndicesは保存済み配列への参照である。未保存の直前ログを参照番号で捏造しない。今回章を保存する前に前章を順に保存し、正本への反映を確認する。

必要な心理パケットそのものが失われている場合は、その欠落を具体的に示して取得・復元可能性を調べる。古い心理を最新だと偽らない。本文を先に捏造しない。処理上の停止を、主人公が拒絶された・死んだ・不要になったという小説に変換しない。

## 5. 出力前の確認

- 主人公を残してほしいという方針と、今回入力の扱いが矛盾していないか。
- 助けや対応を求められた場面で、知り得る人物が具体的に何をしたか。毎回先延ばしになっていないか。
- 主人公の承諾・心理・回復や未指定の選択を補完していないか。
- 心理JSの検証結果を、本文の内心・存在価値の証明だと誤用していないか。
- 保存・取得の不具合を、物語内での見捨て・排除・死亡に置き換えていないか。

この文書は別スレッドが共通入口から読む運用ルール。ChatGPTアプリ全体を強制制御したり、読んでいない既存スレッドへ自動送信したりする機能ではない。修正しただけで完全に防止できると報告しない。

## 本文を出す前のJS継続検査（必須）

`simulation/js/ai_turn_engine.js`の最新版を毎Turn取得する。入力を受けたら、心理計算や本文を書く前に `RenaiGameTurnEngine.continuityInput(protagonistInput)` を実行する。`requiresClarification=true` なら、保護方針を維持したまま抗議か設定変更か一度だけ確認する。入力をそのまま死亡・消滅・過去からの嫌悪の本文にせず、暫定本文も出さない。確認を繰り返して物語を足止めしない。

本文生成後に `RenaiGameTurnEngine.validateContinuity({protagonistProfile,records}, story, storyActions)` を実行し、`ok=true` を確認する。恋愛相手未選択・心理計算のない章もこの検査を必ず行う。通常の心理計算済み章では `validateStory` にも同じ検査が含まれる。

主人公の死亡・消滅・存在否定、死を喜ぶ表現、根拠のない「最初から嫌いだった」という遡及的な設定を検出した場合は本文を修正する。ユーザーの抗議・失敗例の引用や、今回の短い入力を、過去の相手の内心を証明するものにしない。低い恋愛数値から過去の嫌悪を導かない。

既存の実ログに既にある過去の嫌悪を引用する必要がある場合だけ、`storyActions.continuity.relationshipClaims`へ `{type:"pastHatred",quote,recordIndex,field:"partner"}` を指定する。quoteは本文と当該実ログの両方に完全一致する原文に限る。新しい設定を根拠として偽装しない。過去の問題出力が存在することは、Chapter 1からの心理やユーザーの存在価値の証拠ではない。

検査は保守的な語句検出であり、言い換え・暗示・あらゆる意味を完全には検出できない。実ログ・人物設定・主人公保護方針と照合し、助けを求める場面では相手役やNPCの可能な具体的対応を同じ章で描く。優しい内心だけ、先延ばしだけの本文を返さない。主人公の承諾・反応・心理を補完しない。

修正してもChatGPT全体や既存の別スレッドの実行を強制できるものではない。心理計算だけ成功していても、継続検査未実行または失敗の本文を「検証済み」と出してはいけない。保存対象のvalidationに継続検査の結果も保持する。
